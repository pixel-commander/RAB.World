COMMON STAMP FILES AND THEIR FIELDS

These are the patterns present in the current world, beacon, project and
component scaffolds. Not every stamp produces every file. A stamp's own
files describe how it runs; its template and executor determine what lands
in the destination folder. The two settings.json files have different jobs.

CURRENT OUTPUT EXAMPLES

World: settings.json and README.txt under .rab/worlds/[name].
Beacon: beacon.json inside the chosen folder.
Signal: settings.json, contract.json and README.txt inside the chosen folder.
Component: Name.tsx (or the selected text output), settings.json, README.txt;
  optional dependencies can produce additional files.
React project: settings.json, PATHS.json, README.txt, RULES.txt, package.json,
  tsconfig.json, vite.config.mjs, index.html, .gitignore and src/ starter files.
Magic Box project: settings.json, PATHS.json, README.txt and template folders
  such as output/ and audit-results/, plus Box-owned saved project records.

No universal rule currently makes contract.json or an executor appear in
every generated folder. Those normally remain with the tool that made it.


settings.json:
  Usage: Describes the owner of this folder. At a tool, it declares the
  tool's identity and input form. In generated output, it describes the
  new world, project, component or other item.

  Common fields:
  name: Machine-facing name of this particular owner. A tool's name matches
    its leaf folder; the input field named name supplies the new item's name.
  id: Stable positive numeric identity allocated by the shared owner.
    A tool ID and the IDs of items it creates are different identities.
  title: Human-readable display title.
  description: Explanation of the owner's purpose.
  settings: Array of input declarations, not a bag of submitted values.
    A generated record without configurable inputs can have an empty array.
  meta: Information describing the owner's role or operation.
  indexed: Whether an item participates in the existing settings-based
    inventory. Explicit false is excluded; the shared item owner defaults
    an absent value to true. This is not beacon reach.

  Fields present for particular owners:
  version: Contract version, such as rab-node/v1 for saved world/project nodes.
    It is not currently emitted on every tool or item settings file.
  date_added: Creation timestamp; generated by the world and beacon stamps.
    It is not yet a universal field across older stamps.
  type: Owner-specific classification, such as react, magic-box or component.
  transmitting: Shared boolean discovery declaration. The add/signal scaffold
    defaults it to true and preserves false. Other stamps and scanner behavior
    have not yet been updated to this field; it is separate from indexed.
  paths: Named locations belonging to the owner. New worlds start with an
    array. Existing project stamps still use an object keyed by path role.
    This difference exists today; do not assume all stamps use the new array.
  custom_toolkit_path: Project reference to an external toolkit on disk.
  class: Component styling classes, when that stamp supplies them.
  grid: Selected canonical grid, when applicable.
  areas: Areas supplied by that grid, when applicable.
  parent_path: Containing folder recorded by a component stamp.

  Common meta fields, depending on the owner:
  kind: Record role, for example world, project, component or toolkit.
  source_root: Absolute root of a saved world or project's source.
  domain: Tool family, for example world or react.
  operation: What the tool does, such as create, index or update.
  target_type: What the tool acts on or produces.
  data_types: Categories of data handled by the tool.
  output: Classification of the result.
  authority: Declared operation authority, such as read or write. This
    describes the tool; it is not independent permission to run it.


settings.json -> settings[]:
  Usage: The common connection between the tool and its front-end form.
  Each array entry describes one input; the submitted value is passed to
  the executor in options under that entry's name.

  name: Input key, such as name, path, title or reach.
  type: Input/control kind. Current controls include text, textarea, number,
    boolean, options, json, path, folder, file and settings.
  title: Label shown in the form.
  description: Help text explaining the input and its expected value.
  required: True means the tool needs this input before execution.
  default: Value used when the input is absent. An explicit valid false,
    zero, empty string or empty array must not be replaced merely for being
    empty or false. Each field's actual validation still applies.
  options: Displayable choices for an options control. Each choice has a
    name (submitted value), and may have a title or description.
  enum: Allowed values enforced by the shared binder when declared on a field.
  items: Per-element declaration used by array inputs such as beacon types
    and reach. Their executors currently enforce items.enum; the generic
    JSON form does not implement full JSON Schema validation.
  ask: Used by some existing tools to flag an explicit input choice.
  try: Optional tool reference used by the runner when resolving missing input.

  In the current front end, options renders a single-choice select. json
  renders a JSON textarea; it is not automatically a multi-select control.
  folder and path inputs currently render as text fields.

  Example input declaration:
    {"name":"path","type":"path","title":"Folder Path","required":true}

  Example submitted value:
    {"path":"src/admin/components"}

  These are different objects: the declaration defines the form; the
  submitted value tells the tool where this invocation should write.


contract.json:
  Usage: Describes the tool's implementation source and result shape without
  executing the tool. Usually lives beside the executor, not in its output.

  version: Tool-contract format, currently tool-contract/v1.
  source.kind: How the result is produced: template, internal, hybrid,
    composite, file-operation or unclassified.
  source.description: Explanation of the implementation and its ownership.
  source.reviewed_at: Review date when supplied; not a generated-item date.
  result: Description of the returned object and its fields. Example strings
    here explain a shape; they are not the actual execution result.
  settings: Optional contract description of settings; form input declarations
    still come from the tool's settings.json.
  extends: Relative reference to another contract within the tool boundary.
  select: Optional field used to choose a contract variant, such as name.
  variants: Branches selected by that field's value.

  name: There is no standard top-level name field in the current contract
    format. With select: name, the loader reads the tool's settings.json name.
    result.name describes a name returned by the executor, when applicable.

  The add/signal template also creates a contract.json in its output. That
  contract belongs to the generated signal, not its maker. It starts with an
  unclassified source and empty inputs/results until its behavior is defined.


beacon.json:
  Usage: A folder's declaration to a future indexing updater. It is generated
  inside the target folder, rather than copied into every stamped artifact.

  name: Beacon's name; required input.
  id: Automatically allocated identity, independent of the name or location.
  title: Display title; defaults to name.
  description: Explanation of the folder; defaults to empty text.
  date_added: Automatically generated UTC ISO 8601 creation timestamp.
  path: Required folder path. With a selected world, its root is prepended
    to a relative input. Without a selected world, supply an absolute path.
    The stored value stays relative in the first case, absolute in the second.
  types: Selected categories from ui, docs, tools, audits, functions; defaults to [].
  beacon: on or off; defaults to on.
  reach: Scanner visibility declaration; defaults to ["world", "project"].
    The exact words are world and project. Whether project means the owning
    project or all projects remains undecided. Empty arrays are preserved;
    their visibility meaning also awaits the scanner contract.

  Beacon discovery and enforcement are not implemented by the scaffold.
  This file does not start a listener by existing on disk.


PATHS.json:
  Usage: Project identity and capability registration. This is separate from
  the folder locations stored in settings.json paths.

  project: Project identity: id, name, title and description.
  stamps: Registered stamp addresses and their target identities/paths.
  tools: Registered tool addresses and their target identities/paths.
  catalogs: Declared catalog references; project templates currently start empty.
  Entry id: Identity of the registered capability.
  Entry path: Implementation path for that capability.
  Entry toolkit: External toolkit identity, when that registration needs it.

  Current React and Magic Box project stamps supply this file. The new world
  and beacon scaffolds do not generate it.


manifest.json:
  Usage: An index maintained by its indexing owner, usually after stamping.
  It is not a universal stamp-output file, and different manifests currently
  have different shapes.

  Project inventory manifest:
  id, name, title, description, settings: Common identity and description.
  items: Records keyed by their numeric IDs, preserving source item identities.
  meta.kind: manifest.
  meta.version: Inventory format version.
  meta.collection: Indexed path's current collection key.
  meta.project_id: Project that owns this inventory.
  meta.path: Source location being indexed.
  meta.conditions: Recursive/include/exclude scan choices.
  meta.scanned_at: Time of the scan.
  meta.count: Number of indexed items.

  Current saved location:
    .rab/projects/[name]/manifests/[path-key]/manifest.json

  The high-level .rab/projects/manifest.json is instead an ID-keyed project
  lookup containing id, name, title and description for each project.
  There is no new world-manifest format defined by the world scaffold yet.


listener.json:
  Usage: Saved registration for the existing project-path listener. Created
  when paths are registered, not by every stamp.

  version: Listener contract version.
  paths: Existing object of registrations keyed by project path name.
  Registration id: Listener registration identity.
  type: Named path key in this existing listener; not beacon content types.
  recursive: Whether to descend through nested folders.
  include / exclude: Folder matching patterns.
  debounce_ms: Delay used to combine changes before updating.
  reconcile_ms: Interval for rechecking the watched location.

  This describes the existing listener. It has not been changed into the
  planned beacon-driven world scanner.


SOURCE.json:
  Usage: Provenance for a moved/imported tool, when present. It is not a live
  instruction to execute an old path, and is not routinely stamped into output.

  source_tool_id: Preserved original tool identity.
  source_tool: Former tool address.
  source_root: Historical source location.
  relocated_to: Address recorded for the move.
  note: Explanation of the provenance or relocation.


README.txt:
  Usage: Human explanation of the folder, its purpose and how to use it.
  No fixed JSON fields. A tool README explains its contract; a generated
  README explains the created artifact. Documentation does not start services.

RULES.txt:
  Usage: Applicable implementation and ownership rules. Read before editing
  that area. Present in some project templates; not emitted by every stamp.

<leaf-name>.mjs:
  Usage: Tool executor, such as world.mjs or beacons.mjs. Receives options,
  context, tool and helpers through the common runner contract. Some child
  tools inherit an executor from a parent folder. Normally stays with the tool.

template/:
  Usage: Directory owning the file shapes the stamp fills and writes.
  Files can use replacement markers or structured values filled by the
  executor. Empty template values are not valid finished records until filled.

*.test.mjs:
  Usage: Automated checks for the tool/owner. They are development files,
  not automatically part of the stamped output.


REACT-SPECIFIC FILES

package.json:
  Usage: Node package and build commands, not the house identity descriptor.
  name: Package-manager name, which may differ from the display title.
  private: Prevents accidental npm publication when true.
  type: JavaScript module mode; module means ES modules here.
  engines: Required runtime versions.
  scripts: Commands such as dev, build and preview.
  dependencies / devDependencies: Runtime and development packages.

package-lock.json:
  Usage: Exact dependency resolution produced by npm install, not by the
  current project template itself.

tsconfig.json:
  Usage: TypeScript checking/compiler configuration.
  compilerOptions: Language, module, JSX and checking behavior.
  include: Source locations checked by TypeScript.

vite.config.mjs:
  Usage: Vite development/build configuration and plugins.
index.html:
  Usage: Browser entry page and application mount point.
src/main.tsx:
  Usage: Mounts React into the browser page.
src/App.tsx:
  Usage: Initial application component.
.gitignore:
  Usage: Files and directories Git should leave untracked. Rules are patterns,
  not JSON settings; they do not untrack already committed files.
