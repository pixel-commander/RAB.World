RULE CARDS: MODEL HANDS + UI REVIEW

PURPOSE
One situation per card. Select relevant cards for a task; do not load this entire
file into every small-model request. Keep RULE, USE-WHEN, and examples together.
RULE is the constraint; DO is the form to reproduce. DO-NOT shows the tempting
wrong move. Example snippets are fragments unless a complete function is shown.
CHECK describes intended coverage, not an already implemented checker:
  TOOL  = deterministic assertions about observable facts in a resolved scope.
  MODEL = judgment assigned exclusively to self code review.
  BOTH  = two separate stages: tool facts, then self code review of those facts.
No judgment belongs inside an automated check. Unknown evidence is not a pass.
The self code review workflow lives in code-review/RULES.txt beside this file.
Use existing audit tools (including classname audits) as the facts' owners;
this rule source does not require one script to implement every check.

FINDING DISPOSITION
A detected condition is not automatically a hard failure. The rule determines
its route; judgment and approval remain outside the deterministic checker.
  PASS: The stated deterministic condition was checked and satisfied.
  HARD-FAIL: An unambiguous non-waivable check failed, such as invalid syntax or
    a missing required field. Correct it and rerun; do not wave it through.
  APPROVAL-REQUIRED: A condition was detected that needs an explained decision.
    Keep it unresolved until the reviewing LLM approves within the existing rules
    or requires a correction. Escalate exceptional/high-impact cases to the human.
  UNKNOWN / UNAVAILABLE: Evidence or a checker is missing. Report that limitation;
    do not turn it into a pass, a proven violation, or an invented approval.

An approval records who reviewed, the specific finding, the evidence/reason, and
the applicable exception. Approval concerns this occurrence, not a blanket rule
waiver. A material change to that occurrence requires review again.
The LLM may approve within the user's existing exception/authority. Changing a
binding rule or approving an exceptional departure requires the human's decision.
Use the existing .rab review/run owner for these records, not another registry.

These cards remain one editable source file. They are not newly stamped neurons,
do not allocate neuron IDs, and do not change either source ganglion or its index.
If promoted later, use the canonical neuron stamper rather than hand-writing its
SKILL/RULES pair. Keep code examples whole when selecting/indexing cards.

SCOPE / DIFFERENCES TO PRESERVE
The concepts apply across project types; React examples do not make them global
React file requirements. Read the selected project's current contract first.
Do not silently reconcile these observed source differences:
  * CURRENT uses events-header/events-body; UI P5 and GRID C3 use events__header.
    Use the current example for this new convention; retain an existing project's
    declared dialect unless its migration is part of the task.
  * CURRENT child bags use events_props; GRID N1 generally prefers camelCase.
    GRID N2 prefers inline JSX props unless a bag is reused. The current explicit
    child-bag convention overrides those preferences only for the named child bags.
  * CURRENT Box discovery uses settings.json; UI demo discovery uses settings.ts.
    These are different consumers, not interchangeable registration files.
  * UI C1 names --space-md for pad; GRID/cells/padding names --space-lg.
    Resolve the project's .pad owner; do not hardcode either as house-wide truth.
  * CONDITIONS requires ?. on every condition access; GRID P6 rejects unnecessary
    ?. on required values. Proposed scope: untrusted/optional receivers versus
    narrowed, required values. This is a resolution proposed here, not identical
    source wording; report a project conflict if its exact rules still disagree.
  * GRID/populating always wraps content in .inner; UI C5 excludes that wrapper
    for track-filling, area-owning components. Scope the exception by child kind.
  * GRID cells prohibit all inline styles; CURRENT permits dynamic positioning
    and dynamic colors. Apply the explicit current exception to this new contract.
  * UI R5 discusses width/height; CURRENT did not grant arbitrary dynamic sizing
    an inline exception. Check positioning geometry against the actual contract.
  * CURRENT clarified the structural detector: grid marker -> unmarked wrapper(s)
    -> grid marker. data-grid, data-rows, or data-cols is a marker on any element.
    This detector does not infer display:flex from an unmarked element. Historical
    examples with an unmarked data-area wrapper around a nested grid still match
    the detector; do not silently exempt them based on the older flex wording.
  * The R: ganglion index has hash-based document/chunk IDs. They are existing
    index internals, not the numeric source-item IDs required by CURRENT/UI H7.

Do not treat legacy violations or source conflicts as permission to invent a third
pattern. Retain provenance and report unresolved conflicts before applying a rule.
