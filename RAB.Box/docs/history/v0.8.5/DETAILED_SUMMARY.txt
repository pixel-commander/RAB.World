1. EXECUTIVE SUMMARY
======================================================================

RRAABBIITT Magic Box v0.8.5 turns the earlier green v0.8.4 baseline into a
deeper, more self-similar Tool House where language interpretation, Tool
resolution, nested execution, missing-seat resolution, teaching, and operator
inspection all follow the same contracts.

The central idea is:

  messy / incomplete human language
      ->
  preserve whatever structure is actually known
      ->
  resolve a typed semantic shape
      ->
  resolve a lawful Tool from PATHS + path/tag evidence
      ->
  fill required seats from current Turn / Step / Bag / project / child Tools
      ->
  execute only when the symbolic contract is complete
      ->
  keep the entire chain visible in Task traces and receipts

v0.8.5 is NOT a move toward a giant fuzzy language model deciding everything.
The useful "neuro-symbolic" idea retained is:

  candidate / proposal may be fuzzy
  symbolic contracts own execution authority

The Box can tolerate unknown words without inventing their meaning, but it also
does not waste durable memory recording words merely because they are unknown.

2. CORE SELF-SIMILAR LAW
======================================================================

The recurring runtime law remains:

  CURRENT
    ↓
  CHILD
    ↑
  RETURNED SHAPE + CURRENT
  =
  NEW CURRENT

This is intended to apply at multiple scales:

  - language composition
  - nested Tools
  - Stamps
  - child resolver Tools
  - Steps
  - Bag state
  - project facts
  - generated products
  - future provider wrappers

A child does not own what happens next. The runner owns:

  - parentTaskId
  - child invocation
  - trace chronology
  - returned-seat extraction
  - shared-seat packing
  - parent resume
  - receipts

There is deliberately no callback field that every Stamp must implement.


======================================================================
3. TOOL HOUSE MODEL
======================================================================

Everything invokable is a Tool.

A Stamp is a Tool that materializes a known shape from a template/ folder.

Public capability folders may be arbitrarily deep.

Example:

  tools/react/find/hooks/state-hooks/settings.json

The semantic path is:

  react/find/hooks/state-hooks

and therefore inherited tags include:

  react
  find
  hooks
  state-hooks

Canonical identity model:

  {
    id,
    path,
    tags,
    script
  }

Meaning:

  id     = permanent identity
  path   = current semantic / physical position
  tags   = inherited meaning derived from path
  script = current executor

Important law:

  ID IS IDENTITY.
  PATH IS CURRENT POSITION / SHAPE.

A Tool can move without losing identity.

Path/tag law:

  Path tags are inherited truth.
  Explicit metadata may add meaning.
  Explicit metadata may not contradict the path.

This is important for deterministic capability resolution. A candidate whose path
contains one meaningful extra matching tag should beat a more generic candidate
when the rest of the evidence is otherwise comparable.

Example:

  "find hooks"
      ->
  react/find/hooks

  "find state hooks"
      ->
  react/find/hooks/state-hooks

The second wins because the extra state-hooks semantic evidence is present.


======================================================================
4. MANY SEMANTIC KEYS, FEW ENGINES
======================================================================

The House is allowed to contain many precise semantic leaves without duplicating
implementation.

Example shape:

  react/count/count.mjs
  react/count/hooks/settings.json
  react/count/hooks/state-hooks/settings.json
  react/count/hooks/use-effect/settings.json

The nested public Tools can inherit the nearest parent executor.

This keeps the semantic catalog rich while keeping implementation small.

The same pattern is used for generic find/count behavior.


======================================================================
5. FLAT PATHS ADDRESS BOOK
======================================================================

The filesystem is deep.

PATHS.json remains flat.

That means the House can physically express semantic inheritance while callers
still use short direct addresses.

Conceptually:

  PATHS.stamps["add-component"]
      -> { id, path: "react/stamp-new-component" }

  PATHS.tools["find-hooks"]
      -> { id, path: "react/find/hooks" }

  PATHS.tools["find-state-hooks"]
      -> { id, path: "react/find/hooks/state-hooks" }

The short PATHS key is the direct House address.

The deep path is the current semantic position.

The stable ID identifies the actual capability across moves.


======================================================================
6. PROJECT PATHS OVERRIDE / HIJACK
======================================================================

A loaded project may provide its own PATHS.json binding for the same House
address.

Conceptually:

  HOUSE PATHS
  +
  PROJECT PATHS
  =
  EFFECTIVE PATHS FOR CURRENT PROJECT / BAG

Project binding wins for that project.

The House implementation remains inspectable as shadowed provenance.

This lets a stable intention such as:

  add-component

remain the same human/House key while a particular project supplies its own
implementation.


======================================================================
7. RUN / GROUP / STEP / TURN / TASK
======================================================================

The current terminology remains:

  RUN
    whole working session

  GROUP
    related branch/context of work

  STEP
    one semantic unit of work; may span multiple Turns

  TURN
    one user submit / Enter

  TASK
    one Tool invocation inside a Step

This distinction matters because a user correction does not need to create a
new semantic job. It can repair the same Step.

Resolution precedence is approximately:

  explicit current Turn
  -> current Step
  -> parent/context chain
  -> Bag / Run facts
  -> project facts / .rab memory
  -> previous receipts
  -> legal default
  -> child resolver Tool
  -> ask human

Newest explicit correction beats stale stored memory.


======================================================================
8. GENERIC TOOL CHAINING
======================================================================

Chaining is NOT Stamp-specific.

The same runner contract applies to:

  - Stamps
  - ordinary Tools
  - find/search Tools
  - count Tools
  - resolver Tools
  - importer Tools
  - future provider wrappers
  - any other public invokable Tool subtype

The generic chain is:

  CURRENT
      ->
  CHILD TOOL
      ->
  typed / named returned seats
      ->
  RUNNER-OWNED SHARED SEAT BAG
      ->
  CURRENT RESUMES
      ->
  later sibling / parent / Step may reuse matching seats

The child never owns continuation.

The runner owns continuation.


======================================================================
9. RUNNER-OWNED NAMED SEAT BAG
======================================================================

v0.8.5 adds / proves named-seat propagation across Tool kinds.

A child can return reusable named values through supported return shapes such as:

  result.provided.value
  result.provided.path
  result.provided.file
  result.provided.seats
  result[field.name]
  result.path
  result.file
  continuation.seat + continuation.value

The runner can pack those values into the shared seat state.

A later Tool that declares a setting with the same name may inherit that value
rather than rediscovering it.

Important precedence law:

  explicit current options
      beat
  inherited seat values

This means inheritance helps with continuity but cannot silently override what
the operator just said.

Task traces expose seat changes and provenance so automatic resolution does not
become hidden magic.


======================================================================
10. settings[].try — DECLARATIVE CHILD RESOLUTION
======================================================================

A Tool setting may declare a resolver hint.

Example:

  {
    "name": "css_path",
    "type": "path",
    "required": true,
    "try": "find-folder"
  }

Meaning:

  1. normal context resolution tries first
  2. if the required seat remains empty
  3. the runner invokes the PATHS key named by try
  4. the child Tool returns a compatible value
  5. the runner fills the same named seat
  6. the parent resumes

This is not a callback.

The child is visible as a child Task with parentTaskId and an AUTO reason.

v0.8.5 proves this behavior end-to-end with a public Tool and also uses the
mechanism in the grid/CSS slice.

======================================================================
12. LANGUAGE PIPELINE
======================================================================

The language system is organized as a shape pipeline.

SHAPE 0 — RAW INPUT
  Preserve exact original input.

SHAPE 1 — LEXICAL POSSIBILITIES
  type-mapper.json answers:
    "What could this word / phrase be?"

  It preserves legitimate ambiguity.
  It does not decide execution.

SHAPE 2 — TYPED COMPOSITION / NARROWING
  Uses:
    - order
    - grammar / position
    - phrase structure
    - context
    - known entities
    - already-filled seats
    - hard contradictions
    - explicit type compatibility

  This is where unknown words may receive an inferred ROLE without receiving an
  invented MEANING.

SHAPE 3 — CANONICAL MAGIC BOX SEATS
  Examples:
    domain
    operation
    target
    target_type
    quantifier
    predicate
    relation
    name
    value
    reference
    scope
    output

SHAPE 4 — TOOL CANDIDATES
  Current PATHS / Tool House candidates are generated using domain and path/tag
  semantics.

SHAPE 5 — TOOL MATCH / RANK
  Hard contradictions reject candidates.
  Compatible path/seat evidence ranks survivors.

SHAPE 6 — TOOL SETTINGS / EXECUTION
  Required settings are filled from:
    current Turn
    open Step
    parent/context
    Bag
    project/.rab memory
    previous receipts
    legal defaults
    child resolvers

  Then:
    visible plan
    confirmation / permitted execution mode
    execution
    receipt
    Bag / context update


======================================================================
13. TYPED UNKNOWN HOLES
======================================================================

An unknown word does not have to destroy the whole parse.

Example:

  find fuck-off hooks

The Box can still preserve:

  operation   = find
  target_type = hook

and infer that "fuck-off" occupies a predicate/modifier position.

Transient active-Step representation may look conceptually like:

  {
    value: "fuck-off",
    type: "predicate",
    known: false
  }

The key point is:

  role may be inferred
  meaning is NOT invented

Execution authority remains blocked while a required meaningful seat is
unresolved.


======================================================================
14. UNKNOWN DOES NOT MEAN DURABLE MEMORY
======================================================================

A major law clarified during this work:

  UNKNOWN != KNOWLEDGE

The Box should NOT build a database of words it does not know.

That would waste storage and would be weaker than simply not having the word.

Therefore:

  unknown token
      ->
  may remain temporarily visible in the current Turn / Step
      ->
  may help expose which seat failed
      ->
  is NOT persisted merely as "unknown"
      ->
  disappears unless positively taught

Durable memory is for positive useful knowledge.

Example:

  "hack"

should not create:

  hack = unknown

If the operator intentionally teaches:

  hack means add

then the positive mapping may be saved with provenance.

If the operator simply rephrases:

  add TestKit to GetSome

there is no reason to save "hack" at all.


======================================================================
15. RECOVERY WHEN LANGUAGE IS INCOMPLETE
======================================================================

The current direction is NOT:

  fail -> dead end

and NOT:

  unknown word -> automatically teach it

Instead the Box can use the partial semantic shape and actual Tool House to expose
the missing seat and legal positive fills.

Example:

  input:
    hack a new component named "do-it"

The Box may already know:

  target_type = component
  name        = do-it

but be missing:

  operation

Recovery can therefore show:

  KNOWN
    target_type = component
    name = do-it

  MISSING
    operation

  LAWFUL FILLS FROM CURRENT HOUSE
    add/create
    find
    update
    remove
    ...only if actually compatible with the current shape

The user can then:

  - pick a lawful fill
  - rephrase
  - add more evidence
  - deliberately teach a positive mapping

The exact recovery UX should continue to be tested rather than frozen too early.

A useful possible strategy to test is:

  zero legal fills
    -> ask / rephrase

  exactly one legal fill
    -> propose it

  a small number of legal fills
    -> show choices

  too many legal fills
    -> ask for narrowing evidence

======================================================================
28. BRIDGE / SERVICE SAFETY MODEL
======================================================================

The bridge keeps execution behind server-owned run state.

Important current service behavior includes:

  - client sends run ID + revision
  - stale revision can return conflict rather than silently racing
  - completed run does not execute again through the adapter
  - execution-started state is saved before engine work
  - only files named by a completed receipt are exposed by output viewer
  - language imports are validated data resources
  - no arbitrary shell/file HTTP endpoint
  - local Host / Origin checks
  - no CORS exposure by default

These controls are useful local-workbench protections, but they are not claimed
to be full multi-user authentication or an untrusted-code sandbox.

32. WHAT v0.8.5 DELIBERATELY DOES NOT DO
======================================================================

v0.8.5 does not attempt to solve everything.

It deliberately avoids:

  - making an LLM the final authority
  - persisting every unknown word
  - giant negative rule lists
  - one implementation per semantic Tool leaf
  - callback fields embedded in every Stamp
  - path-as-identity
  - filesystem-shaped PATHS registries
  - hiding automatic child work
  - silently overwriting grid.css
  - forcing every phrase into academic truth-value semantics
  - exception-driven "try left(right), then right(left)" type composition
  - treating every failed wording as something that must be taught

33. IMPORTANT OPEN DESIGN AREA: RECOVERY UX
======================================================================

The architecture now has enough information to make smarter recovery possible.

The exact interaction policy should still be experimentally tested.

For a partial shape, the Box can potentially:

  A. show the missing seat only

  B. show the missing seat plus legal House fills

  C. offer one likely legal fill when there is exactly one

  D. ask the user to rephrase

  E. let the user deliberately teach a positive mapping

The important law is that recovery should be generated from:

  current partial semantic shape
  +
  actual legal Tool House contracts

rather than canned apology text or hallucinated synonyms.

Turn Checker is the proper place to test these strategies.
