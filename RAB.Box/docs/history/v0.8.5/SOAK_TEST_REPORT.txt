REAL BUG #1 FOUND — PROJECT PATH VS LEGACY STAMP WRITE ROOT
-----------------------------------------------------------
Scenario:

  Turn 1:
    add component PathMemoryOne

  Box:
    asks for missing components path

  Turn 2:
    src/components

Before fix:

- the same Step resumed correctly
- settings.json paths.components was saved correctly
- the Step became READY
- execution then failed because legacy new-component still enforced literal write_roots:
    components
- planned destination:
    src/components/PathMemoryOne
  was rejected as outside the old write root

Fix:

Legacy Stamp execution now resolves each declared write root through current
project settings paths when a matching project path key exists.

Example:

  PATHS write root:
    components

  current project settings:
    paths.components = src/components

  effective allowed write root:
    src/components

The mapped value is still validated as a safe project-relative path. If no matching
project path key exists, the declared literal write root remains in effect.

Regression added:

  saved project path is also enforced as the current legacy Stamp write root at execution

Verified result:

- same Step resumes
- current project path becomes execution authority
- component is actually created under src/components

REAL BUG #2 FOUND — PROJECT.json PATH MEMORY WAS WRITE-ONLY FOR GENERIC RUNNER
-----------------------------------------------------------------------------
Scenario:

  project/add/paths
    name = css_path
    path = src/css

The Tool correctly saved:

  .rab/projects/<project>/PROJECT.json

but a later Tool with a matching required seat:

  grid-css
    css_path

still spawned:

  find-folder

instead of reusing known project memory.

That contradicted the intended resolution order:

  current Turn
  -> current Step / Bag
  -> project/.rab memory
  -> child resolver/search Tool
  -> ask human

Fix:

Before settings[].try is allowed to spawn a child Tool, the generic Tool runner now checks
Box-owned PROJECT.json for a path whose key exactly matches the missing setting name.

NAME IS THE SOCKET remains the rule.

Example:

  PROJECT.json:
    paths.css_path.value = src/css

  Tool setting:
    name = css_path
    type = folder

The runner hydrates css_path from project memory before trying find-folder.
Project-relative folder/file values are resolved against the loaded project root for Tool
execution, while the stored PROJECT.json value remains project-relative.

Task trace provenance records:

  source: project-path:css_path
  stored: src/css

Regression added:

  Box-owned PROJECT.json path memory fills matching Tool seats before settings try rediscovery

Verified result:

- grid-css executes with one Task
- no find-folder child is spawned
- src/css/grid.css is created
