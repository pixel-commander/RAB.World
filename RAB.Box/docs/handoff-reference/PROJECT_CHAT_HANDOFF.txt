THE ACTUAL TARGET
-----------------
One human request describes a complete outcome and can resolve into multiple
stamp invocations. The human must not issue a separate turn for every stamp or
manually choose each complementary operation. Internal one-turn workers are still
compatible with this: the run owns the full request and continuations.

Candidate discovery should allow any relevant query concept to retrieve an item.
Discovery is not authorization. Do not execute all results, use the first match,
or silently ignore unsupported clauses/negation. Literal names and destinations
are values to bind, not words required to occur in every catalog entry.

EXACT MATCHING BOTTLENECK
-------------------------
src/components/factory-finder/js/search.ts:21 requires:
    terms.every(term => item.fields.some(field => field.text.includes(term)))

Words are lowercased whitespace splits; fields are flattened metadata values.
All words can occur in different fields. Phrase mode requires a complete string
within a single field. These are intentional search modes, not a semantic planner.

Actual probes on the supplied root manifest:
    react project                    -> 2 all-word matches
    react project test-project       -> 0 all-word matches
    react project container-main     -> 1 all-word match
    full original React request      -> 0 all-word matches

Changing raw every to raw some on the full original sentence retrieves all 18
entries, partly due to short/common substring matches such as 'a'. Add broad
concept retrieval; do not promote its output to execution authority. Preserve the
original complete request separately; words excluded from search are NOT erased
from meaning, negation, constraints or later clarification.

WHERE THE EARLIER PROTOTYPE WAS TOO NARROW
----------------------------------------
Useful pieces: runtime contract loading, typed options, missing-input tickets,
parent/dependency returns, verification and receipt plumbing.
Too narrow: one top-level command construction; findHeads() requires exactly one
capability; parseModifiers() binds the rest to that capability/dependency family.
Runtime also rejects a repeated capability frame in one request. A compound plan
must identify invocations by step/frame, not just by capability: creating two
components legitimately uses the same stamp twice with different inputs.
The prior fixture options/PATHS envelopes need an adapter to the REAL catalog;
the user's manifests must not be rewritten just to fit the demo's inventions.

SCHEMA NOTE
-----------
demo_settings provides useful fields, but cannot alone establish complete script
input semantics. Example: the local React maker explicitly requires save-location
and derives further required inputs from scaffold placeholders. Its demo_settings
only advertises name. Preserve both requirements through a host contract or
explicit adapter; do not assume an empty demo_settings array means no inputs.
Descriptions help retrieval; they do not mechanically declare effects/permissions.
